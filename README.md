# JUW Employer Portal

Standalone web app for internship supervisors and job employers to validate
student-submitted organization proformas and submit performance evaluations
(Internship Evaluation Proforma / Employer Survey). Publicly accessible,
decoupled from the OBE/CQI system (which runs on PHP + MySQL inside the
local network) — this app is React + FastAPI + PostgreSQL.

## Architecture

- **Backend**: FastAPI, SQLAlchemy, Alembic migrations, Postgres (Neon)
- **Frontend**: React + Vite, plain fetch-based API client
- **Auth**: passwordless magic link to the employer's work email; a signed
  session cookie afterward. No passwords stored.
- **Admin**: `/admin/*` routes create engagements (manually or via CSV bulk
  upload) and are protected by a static `ADMIN_API_KEY` header, since this
  app has no separate admin login system of its own.
- **Student data**: this app cannot reach the OBE MySQL database directly
  (different network). `scripts/sync_students.py` performs a one-way,
  read-only sync of student records into this app's own `students` table.
  Run it from somewhere with access to the OBE network (e.g. as a cron job
  on the OBE server, pushing into this app's public Postgres).

## Local development

### Backend
```
cd backend
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # fill in real values
alembic revision --autogenerate -m "init"
alembic upgrade head
uvicorn app.main:app --reload
```

### Frontend
```
cd frontend
npm install
npm run dev
```

Set `VITE_API_URL` in a `frontend/.env` file if the backend isn't on
`http://localhost:8000`.

## Deployment (Render)

`render.yaml` defines two services: the FastAPI backend and the static
built frontend. Push to GitHub, connect the repo in Render, and it will
pick up the blueprint. Fill in the `sync: false` env vars manually in the
Render dashboard (`DATABASE_URL` from Neon, `FRONTEND_URL`, `RESEND_API_KEY`,
`EMAIL_FROM`, `OBE_DB_URL` if the sync script runs as a Render cron job,
`VITE_API_URL` on the frontend pointing at the deployed backend URL).

`ADMIN_API_KEY` and `JWT_SECRET` are auto-generated by Render on first
deploy — retrieve `ADMIN_API_KEY` from the Render dashboard and give it to
whoever (IC/admin) will be creating engagements.

## Data flow summary

1. IC/admin creates an engagement (manually or CSV bulk) via `/admin` routes,
   supplying the student's OBE ID, engagement type, org info, and supervisor
   work email. This also creates the `org_proforma` row and sends the
   employer their first magic link.
2. Employer signs in, sees all engagements matching their work email under
   one dashboard.
3. Employer reviews/edits the org proforma (validates what the student
   submitted).
4. Once validated, the employer can submit the relevant evaluation:
   - Internship engagements → Internship Evaluation Proforma (9 GA-mapped
     indicators + attendance/completion/recommendation)
   - Job engagements → Employer Survey (10 GA-mapped indicators), repeatable
     per academic year, each new year's survey created via a fresh
     `/admin` or dashboard-triggered instance.
